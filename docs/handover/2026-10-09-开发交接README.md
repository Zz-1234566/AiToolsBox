### 2.2 ⚠️ JDK 默认是 8，必须显式设 JAVA_HOME

**这是换机器必踩的坑。** 当前机器实测：

```
$ java -version
openjdk version "21.0.11" 2026-04-21 LTS        ← 命令行走的是 21

$ echo $JAVA_HOME
C:\Program Files\Java\jdk1.8.0_202               ← 但 JAVA_HOME 指向的是 JDK 8！
```

Maven / Spring Boot 插件读的是 **`JAVA_HOME`** 而不是 `PATH` 里的 `java`。
不修的话构建会以 "invalid target release: 17" 或编译失败告终。

**修复（每个新终端都要设，或写进系统环境变量）**：

```bash
# PowerShell
$env:JAVA_HOME = "C:\Program Files\Java\jdk-21"
$env:PATH = "$env:JAVA_HOME\bin;$env:PATH"
java -version          # 确认输出 21（或 17）
mvn -v                 # 确认 Maven 显示的 Java 版本也是 21/17

# CMD
set JAVA_HOME=C:\Program Files\Java\jdk-21
set PATH=%JAVA_HOME%\bin;%PATH%
```

> 实际安装路径因机器而异，用 `dir "C:\Program Files\Java"` 确认。
> 若同时装了 17 和 21，Spring Boot 3.2.5 两个都能编，**只要不是 8**。

### 4.1 证件照去背景换底色（新增工具）

#### 做了什么

新增工具 `id-photo-bg-change`（证件照换背景色）：上传人像照片 → **本地 ONNX 推理**抠出人像 → 合成红/蓝/白底 → 存 COS + 写产物表。

#### 技术方案

- **模型**：`u2netp.onnx`（U²-Net 轻量版），**4.36MB**，随 jar 打进 `resources/models/`
- **推理引擎**：ONNX Runtime **1.22.0**（CPU 版，无需 GPU）
- **算法口径严格对齐 rembg**（`base.py` + `u2net.py`）——该组合经过大规模验证，重新发明只会更差
- **实测性能**：模型加载 ~2s（懒加载 + 双检锁，只加载一次）；**单张推理 146ms**

#### 为什么不用腾讯云（或任何云）人像分割 API

1. **许可证问题**：u2netp 是开源模型，本地推理无授权风险；云 API 的商用条款需逐条核对
2. **合规**：证件照属个人敏感信息，出境/上传第三方存在合规风险
3. **离线可用**：部署环境无外网也能跑
4. **免费额度不确定**：云 API 按量计费，写进毕设方案的「成本」一栏经不起推敲
5. **性能够用**：CPU 单张 146ms，比很多云 API 的网络往返还快

### 4.2 签名 URL 改造（重要，影响全局）

#### 问题

COS 预签名 URL **只有 5 分钟有效期**（`cos.signed-url-ttl-seconds` 默认 300）。
接口返回给前端的 `fileUrl` 就是带签名的临时 URL。

后果：**历史记录里所有链接全部失效，点开就是 403**。
这不只是「工作流运行时可能失效」的小问题（旧 README 的说法），而是
「昨天做的记录，今天一个都打不开」的功能性缺陷。

#### 方案

**DB 存 object key，查询时实时签发。**

```
写入链路：
  上传 → COS 返回 key（file/1/{uuid}.mp3）→ DB 存 key        ✅ 不存一次性凭证
  ↓
读取链路：
  查库拿到 key → 后端用 SecretId/SecretKey 实时计算 HMAC 签名 → 返回可用的新 URL
```

`generatePresignedUrl` 是**纯本地 HMAC 计算，无网络开销，不需要判断是否过期**，
所以「每次查询都重签」的成本可以忽略。

**TTL 同时从 300s 提到 3600s（1 小时）**——前端可能「点开 → 试听 → 再点下载」多步使用，
5 分钟会在中途过期。

#### 存量数据兼容（关键设计）

不迁移、不回刷数据，**在读取时顺手续签**：

```java
// FileStorageService.toObjectKey(url) —— 剥掉域名与签名 query，还原成 key
// https://host/file/1/a.mp3?sign=xxx&q-ak=xxx  →  file/1/a.mp3
```

`signUrl()` 的入参**允许直接传完整 URL 或纯 key**，内部统一经 `toObjectKey` 还原：

- 新数据（存的是 key）→ 直接重签 ✅
- 老数据（存的是已过期的签名 URL）→ 剥掉旧签名 → 按当前 TTL 重签 ✅

**两种数据形态在同一条代码路径上都能工作**，无需写迁移脚本。

还有一个隐藏问题：`input_content` / `output_content` 里可能**整条存着签名 URL**
（上传音频后把地址当输入内容提交）。`HistoryServiceImpl#renewSignedUrls`
把这些文本里的过期 URL 扫描出来替换成新签发的。

#### 涉及文件

```
config/CosConfig.java                       signedUrlTtlSeconds: 300 → 3600
service/FileStorageService.java             + signUrl()  + toObjectKey()  + resolveFullUrl()
                                             + extractExtension() 返回值带前导点的约定说明
service/impl/CosFileStorageService.java     实现 signUrl()；修 buildKey 双扩展名 bug；
                                             setObjectAcl 失败不再吞异常（公开读补偿）
service/impl/LocalFileStorageService.java   实现 signUrl()（本地无签名，拼回 /uploads/ 相对路径）
service/impl/HistoryServiceImpl.java        写库存 key；读库实时签发；+ renewSignedUrls()
service/impl/ToolOutputServiceImpl.java     产物表同样存 key、读出即签发
controller/SegmentationController.java       本地存储返回相对路径 → resolveFullUrl() 补全
```

#### 怎么验证的

```bash

#    SELECT file_url FROM sys_aitools_history_file;  → file/1/xxx.mp3（不含 ?sign=）
```

### 4.3 工作流节点真名

#### 问题

前端结果显示 `n1`、`n2` 这种内部 nodeId，用户完全看不懂哪个节点是什么。

#### 方案

**后端补 `nodeName` 字段 + 前端四级兜底。**

后端（`WorkflowServiceImpl`）：

```
取值优先级：
  1. sys_workflow.nodes 里该 nodeId 的 name        ← 编排时用户自己起的名，最准
  2. sys_aitools_tool.tool_name                   ← 未命名时用工具名兜底
  3. 都取不到 → map 里无此 key → 返回 null        ← 由前端回退
```

关键实现：`buildNodeNameMap()` **整轮只建一次 map**。
SSE 是逐节点逐文件推送的，若每帧查库会退化成「文件数 × 节点数」次查询。

`WorkflowNodeResult.nodeName` 是**出参组装时回填的，不写回 `node_results` JSON**——
历史数据不用迁移，查的时候现填。

SSE 的 `node_start` / `node_progress` 帧也一并带上 `nodeName`，前端无需再靠 `nodeRef` 反查。

前端（`workflowView.js` 的 `nodeNameOf`）四级兜底：

```
1. 后端 WorkflowNodeResult.nodeName     ← 后端补字段后自动生效，无需改前端
2. 运行页上下文里已知的节点名
3. 工具列表按 nodeRef(toolCode) 反查 toolName
4. 兜底显示 nodeId
```

#### 涉及文件

```
workflow/dto/WorkflowNodeResult.java           + nodeName 字段
workflow/service/impl/WorkflowServiceImpl.java  + buildNodeNameMap() / fillNodeNames()
                                               SSE 帧加 nodeName；运行详情回填
frontend/src/utils/workflowView.js             + nodeNameOf()（四级兜底，唯一入口）
```

**现象**：历史记录里较早的文件，文件名显示成一串 UUID 而不是原名。

**⚠️ 无法修复**：必须承认这条数据永久丢失原名。不要试图写脚本「回填」。

**降低优先级的原因**：文件类工具是少数，且规划中工具将逐步改为
「前端解析后只传文本」，届时该表可能整体废弃。

### 9.2 `AGENTS.md` 里的硬性约束（摘最容易违反的几条）

### 9.4 代码风格约定

- **缩进 4 空格**，后端包名全小写

      —— 这不是为了凑字数，是为了避免后人「顺手优化」掉关键逻辑。**改代码时保留这些注释。**

- **中文注释、中文错误文案**，面向用户的文案一律中文
- **日志用 `[模块名]` 前缀**，如 `log.info("[id-photo-bg-change] 抠图完成 ...")`

### 已实现的 AI 工具

工具以 `sys_aitools_tool` 为唯一数据源，前端 `src/config/tools.js` 与之 1:1 对应。
划分为两层，目的是让每个工具都能作为**工作流的原子节点**自由编排：

| 层 | 职责 | 工具 |
|---|---|---|
| **解析层** | 纯转换，**不调用 AI** | 文档提取、录音转写 |
| **加工层** | 调文本大模型，**只吃文字** | 会议纪要、重点提取、工作总结、周报生成 |

| sort_no | tool_code | 名称 | 层 | 接口 |
|---|---|---|---|---|
| 1 | `doc-to-text` | 文档提取 | 解析 | `POST /api/ai-office/doc-to-text` |
| 2 | `audio-transcribe` | 录音转写 | 解析 | `POST /api/ai-office/meeting-minutes/transcribe`（ffmpeg + 双引擎）<br>`POST /api/ai-office/meeting-minutes/batch-transcribe` |
| 3 | `meeting-minutes` | 会议纪要 | 加工 | `POST /api/ai-office/meeting-minutes/decide-route` / `stream` / `json` |
| 4 | `doc-keypoint-extract` | 重点提取 | 加工 | `POST /api/ai-office/document-summary/text-stream` |
| 5 | `work-summary` | 工作总结 | 加工 | `POST /api/ai-office/work-summary/stream` |
| 6 | `weekly-report` | 周报生成 | 加工 | `POST /api/ai-office/weekly-report/stream` |
| 7 | `id-photo-bg-change` | 证件照换背景色 | 图片 | `POST /api/ai-office/id-photo-bg-change`（**本轮新增**） |

**文档提取的三条通道**（实际通道写入响应字段 `method`）：

| 输入 | 通道 | 实现 |
|---|---|---|
| `txt` | `text-layer` | 编码自适应（UTF-8 失败回退 GBK） |
| `docx` | `text-layer` | POI 抽段落 + 表格，**内嵌图片逐张送 OCR 后拼接**（`<80×80` 的装饰图标先过滤掉） |
| `pdf`（文本型） | `text-layer` | PDFBox 抽文字层 |
| `pdf`（扫描件） | `ocr` | 逐页渲染 PNG（150 DPI，**最多 20 页**）后送腾讯云 OCR |
| `png/jpg/jpeg/bmp/gif/webp` | `ocr` | 直接送腾讯云 OCR |

> **Word 内嵌图片为什么要 OCR**：财务/办公文档常把发票、盖章、签名、整页扫描件截图内嵌在 Word 里，
> 这部分**不在文字层中**（POI 抽不到），只能靠 OCR 补齐。
> **为什么扫描件要自己渲染**：腾讯云 `GeneralAccurateOCR` 官方注释明确只支持 PNG/JPG/JPEG/BMP，
> 其 OCR 模块下不存在任何 Pdf Request 类（已核实 SDK 3.1.270 全量 class），故必须先转图片。
> 20 页上限用于控制 OCR 按量计费成本。

**提示词设计**：加工层 4 个工具各 2 条系统提示词（`prompt_use` 区分），共 8 条：

| `prompt_use` | 作用 |
|---|---|
| `format` | 约束**输出结构**（章节、编号、表格、字数上限） |
| `generate` | 规定**角色与处理步骤**（怎么读、提炼什么、什么不能编造） |

### 录音转写双引擎

| 引擎 | 标识 | 实现 | 实测（30 秒中文音频） |
|---|---|---|---|
| MiniMax | `minimax` | `MinimaxClient.chatAudio`（M3 多模态） | 1.6s，纯文本 |
| 腾讯云 | `tencent` | `CreateRecTask` + `DescribeTaskStatus` 轮询 | 5.3s，带时间戳，支持热词表 |

> **腾讯云通道的 3.7MB 限制**：`CreateRecTask` 走 `SourceType=1` 内联 base64 时 `Data` 上限 5MB，
> 反推原始音频上限约 3.7MB。超限时由 `FileCompressService` 自动降码率压缩后重试（最多 5 轮），
> 压不动才返回中文错误提示，不会把腾讯云的英文错误码透给用户。

### 文件压缩组件

| 类别 | 扩展名 | 手段 | 迭代参数 |
|---|---|---|---|
| **图片** | jpg/png/bmp/gif/webp | ImageIO 降质 + 等比缩放 | 质量 0.75 起每轮 −0.05（下限 0.1）；宽度 1600 起每轮 ×0.8（下限 600） |
| **音频** | mp3/wav/m4a/aac/flac/ogg/amr/opus/wma | ffmpeg 降码率 | 逐档 `64k → 48k → 32k → 24k → 16k` |
| **文档** | pdf/doc/docx/txt | **不压缩** | 走 `DocumentParser` 本地抽文字层 |

> **与 `transcodeToMp3` 的边界（勿混淆）**：
> `TranscribeService#transcodeToMp3` 管**格式归一化**（无条件执行）；
> `FileCompressService` 管**大小控制**（仅超限时执行）。

### AI 内容落库截断

`HistoryServiceImpl` 写库前截断，防止超长 AI 输出写满 MySQL `text` 的 65535 **字节**上限。

| 常量 | 值 | 依据 |
|---|---|---|
| `Constants.AI_INPUT_MAX_LENGTH` | 20000 | 喂模型的 prompt 上限 |
| `Constants.AI_OUTPUT_MAX_LENGTH` | 16000 | UTF-8 最坏 4 字节/字符（emoji），16000×4=64000 < 65535 |

切分点用 `offsetByCodePoints` 求出，保证不从代理对中间切开产生乱码。

### 用户角色与权限

| 能力 | admin | user |
|---|---|---|
| 使用所有 AI 工具 / 工作流 | ✅ | ✅ |

### 工作流

- **节点 = 工具**：节点引用 `tool_code`，参数存 `params` JSON
- **数组语义**：N 个输入 → N 个输出，逐项独立处理（并行汇聚时各上游输出保持分离，不合并字符串）
- **执行模型**：按 `deps` 拓扑分层，同层并行，**最多 5 层**
- **类型校验**：保存与运行双重校验连线类型匹配
- **提示词**：节点参数只存 `promptIdFormat` / `promptIdGenerate`；提示词失效时**明确报错提示重选**，不静默回退

| 接口 | 说明 |
|---|---|
| `POST /api/workflow/save` | 保存（新建/覆盖），保存即校验 |
| `GET /api/workflow/list` | 列表（含节点信息） |
| `GET /api/workflow/{workflowId}` | 详情 |
| `DELETE /api/workflow/{workflowId}` | 删除 |
| `POST /api/workflow/{workflowId}/run` | 运行（同步） |
| `POST /api/workflow/{id}/run/stream` | **SSE 流式运行** |
| `GET /api/workflow/runs` | 运行历史列表 |
| `GET /api/workflow/runs/{runId}` | 运行详情（含每节点输入输出 + **nodeName**） |

**相关表**：`sys_workflow`、`sys_workflow_run`、`sys_tool_output`。
